交互验收（详版 §八）重点问题

实测发现的具体缺陷：
  • Wizard 没有撤销。Editor 有 50 步 undo/redo（不持久化），Wizard 全程无 undo —— 只有「清除该指定制」和「退回草稿」。改错底色只能靠记住原值，而模板默认色 #8A625A 不在 8 色色板里，改了就回不去

4 · 模块 B · 3D 预览定位

核心结论：当前阶段不要做 3D。产品需要的不是三维，是「二维高保真」。

最关键的事实：这个项目没有 3D

package.json 的 dependencies 只有 immer / lucide-react / react / react-dom / react-router-dom / zustand —— 没有 three.js，全仓无 three import。所谓「3D 单甲检查」是 Nail3DCheck.tsx 里 269 行自研 Canvas 2D 软件光栅化器（画家算法 + 法线着色）。

它实际渲染的是什么

  • 模块级常量 const MESH = buildShell(14, 18)，半轴硬编码 0.55 / 0.9 / 0.28
  • 因此不读 shape-params.json、不随甲型变、不随长度变 —— almond 与 stiletto 在这里长得一模一样
  • 不显示底色、不显示图案：实体着色固定用品牌色 [194,73,122]
  • 这直接触犯项目自订红线（DEV-PLAN §9）：「几何实现只认 nails-shape-svg skill 脚本；禁止第二参数源 / 第二几何实现」
  • Wizard 侧的「3D 预览」按钮为 disabled（「即将推出」）—— 主流程里根本没有 3D

速查版「3D 不应该做的事」逐项打勾

不应该做的事当前是否犯实测
不必要的自由旋转（顾客会晕）犯了onPointerMove 自由拖拽偏航 + 俯仰，pitch 限幅 ±1.4 rad，无吸附、无预设视角约束
复杂相机控制（美甲师不是 3D 设计师）轻微只有拖拽旋转 + 一个「固定侧视机位」复位按钮，没有平移/缩放/FOV —— 克制得不错，但仍要求用户理解三维空间
对设计决策无帮助的材质光照炫技犯了法线着色 + 实体/线框切换，全部与设计内容无关

推荐定位

美甲师和顾客要回答的问题只有五个：这个颜色好看吗、这个图案在我的甲型上比例对吗、十指搭在一起协调吗、重音指放哪根、长度合不合适。这五个问题全部可以在 2D 里回答得更好、更快、更便宜。3D 只能回答第六个问题——「这个结构做得出来吗」，而那是生产端的问题，且正式几何由算法组产出，现在自研只会产生第二套真相。

必须在 2D 完成未来（算法组正式 STL 到位后）才需要 3D
选甲型、长度浮雕高度与曲面的真实关系
选模板 / 风格边缘刮手、甲片内弧贴合
改底色、图案参数、法式宽度、猫眼角度最小壁厚与打印可行性
逐指例外与重音指正式 STL 与预览的一致性对账
十指整体搭配—
单指细节确认
顾客确认展示

当前必须具备的「立体感」能力（注意：全部用 2D 实现）

甲面纵向渐变 + 高光带 + 甘皮阴影 + 甲尖厚度暗边。这四层就能让平面甲片看起来是有弧度的实物 —— Editor 的大图已经证明这条路走得通（见 §10 图 5）。

当前不应该做的 3D 能力

真实手模贴合、自动曲率变形、UV 映射、自由浮雕编辑、参数化建模、实时布尔、AR 试戴、自动生成生产模型 —— 全部延后，无一例外。

如何避免变成「简化版 Blender」

守住三条线：① 用户永远不操作相机、不操作坐标、不操作变换矩阵；② 任何自由度都以预设档位出现（少/标准/丰富，S/M/L），不给连续滑杆；③ 每新增一个控件，必须能说出它替代了美甲师原本哪一个手工动作，说不出就不加。
按这三条，当前 Editor 的画笔 / 橡皮 / 导入图片 + x/y/scale/rotation 连续滑杆已经越线——这也正是它被降级为「进阶模式」的正确理由。建议进一步从首发验收路径中完全移除。

问题一 · relief 路由不存在，导致首发 Top 3 的招牌结构做不出来

DEV-PLAN §5.9 写明：0.3mm 是 uv25d（UV 喷绘）路由硬上限，而水滴 ≤1mm、花瓣 ≤0.7mm 走 relief（3D 打印结构件）路由，由 routeAttachment() 按 heightSource + maxHeightMm 自动分流。

问题二 · P0 风险筛查的覆盖面与命名不匹配

Q3 说明书列出的可制造性检查项是：是否贴合甲片曲面、是否悬空或穿模、最小壁厚是否足够、边缘是否易断裂或刮手、是否方便清洁佩戴、是否需要支撑、是否适合一次打印、是否适合喷绘和后处理（共 8 项）。

risk.ts 实际检查 3 项，且全部限于附件层：附件数量 >4、heightMm >0.30、边缘邻近。其中边缘判定用硬编码常量 EDGE_X_UNITS = 45，不按当前甲型轮廓计算——在 stiletto 尖部，实际半宽远小于 45 单位，附件可能已经出界却仍然通过检查。

现在就该做的三项预留（低成本，避免 MVP 后重写）

这一节的绝大部分内容都不应该现在建设——正式工艺映射引擎由算法组产出（8/3 到岗）。但有三件事必须现在做，否则后面一定要重写：

  1. 为 shape-params.json 预留工艺补偿字段。加入 process_compensation: { shrink_xy: null, shrink_z: null, min_feature_mm: null, source: "pending-algo" }。现在填 null 无成本；等算法组给值时只改数据不改结构，避免动这个被前端画布、NailSlot 占位、Mock STL 多处消费的核心文件。
  2. 把 routeAttachment() 立成真函数（即使只有两条分支）。让 heightMm ≤ 0.30 → uv25d、> 0.30 → relief（当前返回 unsupported 并给出可读提示）。这样 relief 是「明确不支持」而不是「概念不存在」，Recipe 里的 relief 图层也有了落点，未来接算法组只需替换分支实现。
  3. 把「预览 ≠ 实物」的免责说清楚。顾客确认模式与导出 PNG 上标注「颜色与立体效果以实物为准」。当前 finish 完全无效、色域未校验，却在向顾客展示 sRGB 纯色——这是会产生真实客诉的诚实性缺口，一行文案即可缓解。

截图好看 + 一键对比图		 不通过 无对比图能力，无分享能力。导出只有一种形态：整张 1200×900 的横向 plate PNG（export-png.ts 固定尺寸，scale=2）。问题有三层：① 无「改前/改后」对比图生成；② 无竖版/方版社交尺寸（Instagram Story 9:16、Post 1:1 都不支持），横版 4:3 在社交平台是最差比例；③ 画面主体是装饰性水彩色块与植物 —— 大部分像素给了背景，不是给了美甲。作为一个靠视觉传播的品类，这是被放弃的免费增长渠道
零学习成本
顾客展示模式不看说明书就懂		 不通过 不存在顾客展示模式。顾客只能和美甲师一起看同一个编辑界面：左侧 12 张模板卡 + 七个风格标签、右侧 8 色板 + 质感下拉 + 四个按钮、底部「打开自由画布」。顾客要在这堆控件中间自己找到那个 450px 的预览区。
顺带：状态机本身是干净的（确认 → 冻结只读 → 可退回草稿），缺的只是一个展示容器，不是缺逻辑

关键洞察：保真度是存在的，是呈现尺度把它毁掉了

同一份 pattern SVG，在 Editor 单甲画布（约 200×320px）与十指平铺（约 130px/指）里渲染出来是有说服力的：猫眼渐变、金属流线、水滴高光都清晰可辨。这说明不需要新渲染器，只需要把甲面放大。这是全报告中投入产出比最高的一条结论。

9 · 手艺端快速检查（Cloudia） 本轮全新审查

这一节审的是「软件产出的方案，在真实美甲台上做不做得出来、做完会不会被投诉」。详版完全没有这一层，而它恰恰是「软硬件解决方案」与「设计软件」的分界。

检查点判定实测
预估时间准确
全流程时间可控，不忽悠顾客		 未实现 全仓无工时/耗时/预估相关字段或计算（grep 命中项全为 CSS 类名 duration-fast 之类的误报）。软件无法回答顾客最常问的第一个问题：「这个要做多久？」而这些信息本可低成本从设计推导：附件数量、relief 件数、逐指例外数、长度档位都是已有数据
材料可获取
设计里用的胶/色/饰件店里有货		 未实现 无库存/材料概念。但要注意这里的语义差异：本产品是打印 + 喷绘方案，多数颜色由设备产出而非瓶装色胶，因此「材料」实际指向树脂型号、墨水色组、封层胶。当前这三者在软件里都没有对应对象（Device 类型只有 alias / type / status / deviceCode，无耗材信息）。风险不在缺库存表，而在于设计时无从得知本店设备能否产出该配色
容错空间
某步做坏了能补救		 部分 软件层容错不错，工艺层容错为零。软件层：Editor 有 50 步 undo/redo；确认可「退回草稿」解冻；可「基于已确认设计创建新版本」；保存失败自动重试 3 次 + 手动重试；单指渲染失败其余 9 指正常降级 —— 这些都做对了。缺口：① Wizard 全程无 undo（改错底色回不去，且模板默认色不在色板内）；② undo 栈不持久化，刷新即丢；③ 工艺层无「某指打印失败可单独重打」的概念（设计与生产单元未分离）
客诉预判
起翘/断裂/色差/持久度有防线		 仅一条 四类客诉里只有「起翘」被间接覆盖：risk.ts 的 edge_near 建议文案提到「避免边缘刮手与封层起翘」（但判定用硬编码 EDGE_X_UNITS=45，不按甲型轮廓算）。断裂：无最小壁厚/长度-强度校验（extra-long 26mm 与 short 14mm 受同等对待）；色差：无色域校验，且 finish 完全无渲染差异却仍向顾客展示 —— 这是最可能引发实际客诉的一项；持久度：无相关概念
操作可持续
连续做复杂款不会累崩		 存在隐患 软件侧的疲劳来源已经可见：① 每指 11–17px 的点击热区，连续操作十指对眼睛和精度都是负担；② 无键盘选指（Wizard 只能点画布上的小甲面；Editor 有 L1–R5 按钮，Wizard 没有）；③ 无批量操作（如「除拇指外全部换色」）；④ 无设计复用检索（每单从模板重新开始）。这些叠加起来，会让「一天做 8 单」变成明显的操作负担
本甲适配与前置流程兼容
薄/软/有旧甲；卸甲/修型/建构		 未考虑 这是本节最重要的缺口。Customer 类型共 13 个字段，与本甲状态相关的只有两个自由文本备注（allergyNotes 过敏备注 —— 这一项做得对，安全相关字段存在；preferenceNotes 偏好备注）。没有任何结构化的本甲字段：甲面厚薄、软硬、甲床长度、旧甲残留、是否咬甲、损伤史全部缺失。
更关键的是：前置处理（卸甲 / 修型 / 建构）完全不在数据模型与流程内，而穿戴甲的贴合度与持久度主要由本甲状态和前置处理决定。当前 twinStatus 是从 customer.id 伪造的三态 Mock，不含任何几何量；UI 上也没有任何地方可以录入十指实测尺寸（连量尺路径都没有）

手艺端补审带来的一条新认识

上一轮我把产品定位为「设计工具」，因此结论集中在视觉与流程。手艺端这一节让我看到：产品目前把美甲师当作「配色操作员」，而不是「手艺人」——它不问本甲状态、不管前置处理、不估工时、不预判客诉，也就无法参与美甲师真正的专业判断。

但这不意味着现在要建这些模块。正确的做法是在阶段 B 加两个最小字段先把语义占住：① Customer 增加结构化 nailCondition（薄/正常/厚 × 软/正常/硬 × 有无旧甲，三个枚举即可）；② DesignSummary 增加只读派生的 estimatedMinutes（由附件数 + 逐指例外数 + 长度档推导）。两项都是数据层小改，却能立刻让软件开始「懂手艺」，也为后续贴合度算法留下输入位。

10 · 最高优先级问题 Top 5

按「最快验证真实用户价值 + 不形成严重技术债」排序。P1/P2/P4 沿用上一轮并已复核；P3 因 §7 补审升级；P5 合并了新发现的生产链路声明失真。

P1

主画布把已有的视觉资产亲手毁掉了

事实预览 SVG 实测 450×337px；十指热区 11×17 – 17×25px；布局 grid-cols-[440px_1fr_300px]，左栏模板库比画布还宽。同一资产在 Editor 200px 下明显好看（图 5 vs 图 6）
用户影响P 端无法判断改动对不对（改底色只见 15px 色块变化）；C 端完全看不清买的是什么
产品影响「3 分钟出十指确认卡」在数字上可达成，但产出不具备成单能力，指标失去意义
工程影响极低。不需要新渲染器，只需重排版面 + 加单指放大视图
推荐方案中栏改「十指总览（放大至画布短边 80%）+ 常驻单指大图」双区；模板库收敛为 220px 抽屉或顶部横条；模板卡片改按压/悬浮才展开大图
为什么优先投入产出比最高：成本几乎最低，却直接决定产品能否被演示与验证。所有其他改进都建立在「用户能看清」之上——包括 P4 换底图，在 11px 下换了也看不出来
P2

缺「单指细节」与「顾客展示」，唯一出路是一条会丢数据的单向门

事实Wizard 无缩放/无详情/无展示模式，3D 按钮 disabled；唯一出路是不可逆桥接。wizardToEditorDoc() 写死 attachments: [] / fingerLocks: {}，丢弃全部 fingerOverrides（实测：Wizard 给左中指加珍珠 + 单独底色，桥接后消失）。警告文案未提此损失，却承诺了不存在的「添加文字」
用户影响做完最能体现设计感的「重音指」，点一下按钮就静默丢了，且被告知不可逆 —— 会让人不再信任软件的那类 Bug
产品影响「十指整体 ↔ 单指细节」是美甲设计基本心智，缺失导致产品只能做配色不能做设计；顾客确认也没有专门载体
工程影响中。补 override 转换是小改；展示模式是新的只读视图，可复用现有渲染组件
推荐方案① Wizard 内置单指详情面板（点指即放大，不跳页）；② 新增只读「顾客确认模式」全屏页（大图 + 十指条 + 甲型长度色号文字，隐藏全部编辑控件，并标注「颜色与立体效果以实物为准」）；③ 桥接补全 overrides，警告文案据实修正
为什么优先与 P1 合起来才构成完整的「设计—确认」闭环；其中的数据丢失是当前唯一功能性 Bug 级问题
P3

生产链路整段缺失，且文档已将其描述为存在 因补审升级

事实src/studio/pipeline/、material-library/production-profiles/、Phase 0 三件套均不存在；routeAttachment() 全仓 0 次；3MF 与点胶路径 0 次；60 条 STL 全为 MOCK 且新增 2 模板无条目；色域/最小特征尺寸/收缩补偿三项连定义都没有；ManufacturingPackage/scanContext 为死类型。相对地，浮雕 ≤0.3mm 硬约束四处一致落地，守得很好
用户影响当前不直接影响（原型期 PNG 唯一导出，STL 不暴露给用户）。但 relief 路由缺失意味着首发 Top 3 的立体招牌元素全都无法表达
产品影响触发速查版模块 E 的一票否决。更严重的是认知风险：文档描述与代码现实脱节，会让「距离硬件闭环还有多远」被系统性低估
工程影响若不预留，算法组交付后需改动 shape-params.json 这个被多处消费的核心参数源，以及新建整条 pipeline 与 Recipe→relief 的映射
推荐方案不建设，只预留（§7 末三项）：① shape-params.json 加 process_compensation 占位字段；② routeAttachment() 立成真函数（relief 分支明确返回 unsupported + 可读提示）；③ 顾客展示与导出加「以实物为准」免责文案。同时修正文档，让声称与代码一致
为什么优先它不阻塞演示，但阻塞正确的路线判断；且三项预留成本极低，越晚做越贵
P4

底图不具备佩戴可信度，且完全没有肤色适配

事实唯一一张底图，无皮肤填色、无甲床/甘皮/指关节，装饰性水彩与植物占大量画面；slot 轮廓窄于手指 15–20%；tokens.css 三个肤色 token 全为浅暖调且已是死代码；t_liquid_velvet_cat_eye 默认底色 #8A625A 浑浊且不在 8 色色板内（改了回不去）
用户影响C 端「一眼理解 / 真实感 / 肤色适配 / 心动 / 传播」五项全不成立；对美国市场而言肤色缺失是产品-市场层面问题
产品影响这是「美甲软件」与「美甲游戏」的分界线，也是能否替代「给顾客翻 Instagram 图」的关键
工程影响低 —— 换资产不换代码（manifest 驱动），但需重走 Slot V2 标定 + 人工签收流程
推荐方案换真实女性手部照片底板，至少 3 档肤色（浅 / 中 / 深，覆盖美国主要消费群体）；甲片加甘皮阴影与侧壁高光两层；砍掉装饰性水彩与植物；修正 slot 宽度至贴合指尖；default_base_color 全量重挑并纳入色板；导出增加竖版/方版社交尺寸与改前改后对比图
为什么优先决定 C 端天花板。必须排在 P1 之后——在 11px 尺度下换任何底图都看不出差别，先解决尺度再解决底板，否则做了也验证不出来
P5

交付真实性与工程护栏不足，会让后续判断失真

事实无测试基建（无 vitest / playwright.config / *.test.ts），文档声称的「e2e 17/17」实为单个未挂 script 的冒烟脚本；唯一单测当前失败（rotationDeg 5.81 > 5）；validate-assets.py PASS 但校验的是 archived legacy 资产而非运行时的 V2 slots；单个设计占 256KB localStorage → 约 19 个设计后保存失败；文档与代码六处脱节（Palm 仍在 Editor、pipeline/production-profiles/Phase 0 不存在、契约层与 recipes 零消费、STL manifest 未跟进）
用户影响间接但严重 —— 门店试用时会遇到「保存失败」且无法恢复
产品影响进度报告不可信，下一轮决策会建立在错误的完成度认知上
工程影响中。缩略图外移与修脚本都是常规工作量
推荐方案① 缩略图降为单指裁剪（<15KB）或迁 IndexedDB + 配额兜底；② 修 slot 断言（放宽并写明依据，不得为过测试而改已签收标定值）；③ validate 切到 V2 slots；④ Editor 的 Palm 切换器按 v1.4.1 决策下架；⑤ 契约类型与 recipes 明确标注「未消费」；⑥ 补 npm test / npm run e2e
为什么优先不阻塞演示，但阻塞可信的进度判断，必须在下一轮开始前收口

13 · 五问结论

两份 Prompt 共同要求的最终五问。

问题一 · 现在最应该做的三件事

1. 把画布尺度改对  ·  2. 补上「单指细节」与「顾客展示」并修掉桥接丢数据  ·  3. 给甲面加四层立体感

这三件的共同点是：都不需要新技术，都在两周内可完成，且完成后产品性质会改变——从「能演示流程」变成「能拿去验证价值」。第一件几乎零成本却改变一切：产品已经有能看的资产，却在 11px 里展示它。

问题二 · 现在最不应该做的三件事

1. 不要做真 3D  ·  2. 不要再扩展 SaaS 脚手架与内容广度  ·  3. 不要现在落地 Recipe 参数化渲染器

不要引 three.js、不做曲率变形/UV 映射/AR，现有假 3D 应直接下架。不要加权限、后台、报表；不要把 12 套模板扩到 20 套；不要急着开放剩下 5 个甲型——宽度不解决说服力问题。Recipe 渲染器方向正确，但在「用户看不清、底图不可信」之前落地，等于把最贵的引擎装在看不见的地方。补充一条：也不要现在建生产链路——只做 §7 末尾那三项低成本预留。

问题三 · 3D 投入是过重还是过轻

名义过重、实质过轻、位置错误 —— 净结论：把 3D 预算全部转给 2D 保真度

过重：269 行自研光栅化器，忽略甲型、长度、颜色、图案，且构成第二套几何真相源、违反自订红线，换来零决策价值——这部分应当归零。过轻：产品真正需要的「曲面可信度」投入为零。位置错误：它出现在「检查」，而不是出现在「让顾客心动」。

问题四 · 下一轮更偏产品 / 交互 / 视觉 / 工程

视觉优先，交互紧随，工程只做必要收口，产品定义暂缓

建议配比：视觉 / 渲染 45%（尺度重排 + 立体感 + 3 档肤色底板准备）、交互 35%（展示模式 + 单指详情 + 去掉建档与验证码门禁）、工程 20%（数据完整性 + 存储 + 护栏 + 生产链路预留）。不要在这一轮做新的产品定义——现有定义足够支撑一次真实验证，缺的只是让它「看得见」。

问题五 · 哪个假设最需要尽快找真实美甲师验证

「美甲师愿意用 Studio 生成的预览图，代替翻 Instagram 参考图，直接向顾客展示并成单。」

这是整个产品的地基假设，且目前完全未被验证——而当前实现恰恰在削弱它：用真实照片吸引选款、用低保真矢量图交付结果。
验证方式很轻：完成阶段 A 后，让 3 位美甲师各服务 3 位真实顾客，只记录两个数字——顾客看完预览图后是否要求「再看看别的参考图」，以及是否直接确认下单。如果美甲师仍然要打开 Instagram，那么无论流程多顺、模板多全，产品都还没有成立。
这个信号会直接决定「底板换真实照片 ×3 肤色」与「Recipe 参数化渲染器」这两笔大投入到底值不值得下。

第二顺位待验证假设（来自手艺端补审）：「美甲师愿意在软件里录入本甲状态，以换取更准的贴合度与工时预估。」如果答案为否，那么整条 scanContext / NailTwin 路线的产品价值需要重新评估。
